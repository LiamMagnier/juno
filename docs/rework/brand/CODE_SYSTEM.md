# Alevr Code — coding design system

Working specification · 2026-10-01. Read with BRAND_IDENTITY.md, NAMES_AND_ICONS.md and the existing CODE_AGENT_SPEC.md. Image: assets/alevr-code-system.png.

## Purpose and distinction

Professional agentic coding: understand a task, work in the correct project, inspect changes, verify results and continue with accountable evidence. Code shares Alevr's identity but uses denser operational composition, stronger monospaced structure and explicit review. Its mathematical direction is precision and iteration; Orbit's cosmic/character world does not become coding wallpaper.

Display name: Alevr Code; navigation: Code. Entry-point line: What will you build? Identity-board line: Build. Review. Continue. These are visual copy proposals, not new runtime guarantees.

## Component system

| Surface | Design contract |
|---|---|
| Shell | V3 inset framed panel, operational sidebar, persistent sessions and actual workspace/host context |
| Start | Quiet serif entry point and no-shadow composer with project context; no decorative terminal hero |
| Session transcript | Readable request/reasoning summaries/tool activity; real progress, questions and approvals |
| Context | Project, branch, files and host shown plainly, with meaningful controls; machine values remain mono |
| Changes | Dedicated file/diff panel next to conversation when space permits; readable line numbers and meaningful add/remove colors |
| Review | Explicit Review changes action; truthful pending/accepted/error status and recoverable state |
| Terminal | Actual output, stable readable mono; copy/search/wrap controls without novelty decoration |
| Preview / Computer | Useful operational views; actual input/control boundary and permission behavior |
| Plan / questions | Clear editable plan and concise decision controls; preserve existing question/approval protocols |
| Verification / receipt | What ran, what passed/failed, what remains; never turn a generated example into a real test claim |
| Remote / phone | Adapted density and view navigation; actual host/context remains understandable |

## Palette and typography

Use the exact shared charcoal/light foundations and lifted dark blue from BRAND_IDENTITY.md. Do not add a cyan/neon developer palette. Green/red are semantic diff/data/error colors only. Inter carries operational UI; JetBrains Mono carries code/log/path/branch values; Newsreader appears at identity and entry points, not inside dense code listings.

The Code board favors dark composition but light is independently specified and shown. Dense work should reduce ornamental space, not hit targets or reading contrast. Group by surface hierarchy; avoid boxes around every event and pills around each task status.

## Icons and interaction

Secondary product glyph: opposed open brackets with an inset cursor, built from the shared fine-stroke family. It does not replace the master application mark. Terminal, branch, commit, diff, review, preview, computer, permission and receipt draw from the semantic map. Existing package/export identifiers remain stable.

Use V3 timing and reduced-motion behavior. Real streaming/tool events own feedback; decorative code rain, spinning logos and character gestures do not report work. Preserve immediate Stop response, deterministic approval handling and truthful completion/error states. Tone and label changes carry most interaction feedback.

## Outputs and review

Continuum is the selected master mark; brackets/cursor remain the Code feature glyph. Apply MOTION_AND_THINKING.md to actual reasoning, tool activity, verification and review without changing runtime/approval semantics. The current board is a concept reference, not a finished asset library.

The separate Code board demonstrates master/product lockup, bracket construction, dark workbench, shared palette plus meaningful diff accents, serif/mono pairing, semantic glyphs, light entry point and approval/receipt components. It does not claim the example code was executed. The implementation spec still governs tool/runtime semantics; the brand system changes presentation only when the owner later authorizes it.
