# Agent computers, October 2026: the build plan

Plan only. Nothing in this document is built yet. Written 2026-10-27 against `7c91a0c2e`
(main, live in production). **Revision 2**, the same day, after an adversarial review of
revision 1: section 10 maps every review finding to where this revision resolves it, and
says where and why it disagrees. It is the contract for six build stages, S1 to S6. The
stages do not edit this file; S6 appends a "Result" section at the end.

The owner's ask: Orbit agents that really work and can start their own Linux computer.
The hard rules that bind every stage are in the brief; the ones that shape this plan:

- Production stays off by default. An empty `COMPUTER_PROVIDER` (or
  `AGENT_COMPUTER_PROVIDER`) means no computers, exactly as today.
- Gates are added, never removed or weakened. The per-action floors stay:
  `computer_shell`, `computer_type` and a text-producing `computer_key` are `sensitive`
  and ask every time. Unattended runs never get a standing grant to run commands.
- No deploys, merges, billable actions, live credential changes or commercial changes.
  New owner-tunable numbers go in env with conservative defaults and are listed in
  `docs/OPEN_DECISIONS.md` as "owner to confirm".
- Anything not executed is reported as `not_run` or `unverified`.
- There are no AI provider keys on the build machine. Every model-driven test or demo
  uses the scripted Work model (S1) and says so.

## 0. Order of work

```
Phase 1:  S1 (gating, quotas, policy, self-start, scripted model, honesty)   ∥   S2 (container, image, network, takeover primitives, retention, docs)
Phase 2:  S3 (remote computer host, RemoteComputerProvider, tunnels, relay)
Phase 3:  S4 (real-container end-to-end tests in CI)   ∥   S5 (streamed shell, terminal pane, binary files, inbox, publish)
Phase 4:  S6 (local end-to-end demo of the real product, screenshots, UX fixes)
```

A stage starts only when every stage of the previous phase has finished and reported.
Two stages in the same phase never own the same file (section 3).

### Deviations from the lead's decisions, and why

- **D1. The store-level takeover wiring moves from S2 to S1.** Freezing at take over,
  thawing and rotating at hand back and at lapse, the `takeover_lapsed` audit and the
  wake/sleep/hand-back audit all live in `src/lib/computer/store.ts`, which S1 must own
  for gating and metering. A file has one owner per phase. S2 builds the provider
  primitives (`freezeAgent`, `thawAgent`, `browserSandbox`, `isOutdated`, `imageInfo`) and
  proves them on a real container; S1 wires them with the fake provider; S4 proves the wiring end to
  end on a real container. The security content of decision 6 is unchanged.
- **D2. Audit goes to a new table, `AgentComputerAudit`,** not to `AgentEvent` (the
  person's visible agent log, which rest/wake every few minutes would flood) and not to
  `WorkAuditEvent` (its writer, `src/lib/work/audit.ts`, belongs to another job). The
  existing visible events (`takeover_started`, `takeover_ended`, `computer_enabled` …)
  stay as they are.
- **D3. The freeze stops every agent process and cuts the agent's display connections.**
  Revision 1 killed `xdotool` and `scrot` by name and then ran one `pkill -STOP`: a fork
  loop outran the scan, a renamed or copied injector survived, a command that passed the
  takeover fence just before the window opened started after the freeze and ran unfrozen,
  and a chord killed half way left Ctrl held down for the person. Now, at take over: (1) a
  frozen marker is written as uid 1001 where uid 1000 can read it, so no new agent command
  starts (the exec launcher refuses, D13); (2) `kill(-1, SIGSTOP)` runs as uid 1000, repeated
  until a `/proc` scan finds no uid-1000 task outside state T (the kernel signals the whole
  set in one pass under the task-list lock, and a fork caught in progress either hands the
  same signal to its child or is restarted, so a fork loop cannot escape; the caller is
  excluded; the verification scan, not this reasoning, is what the tests rely on); (3) as
  uid 1001, every X client whose PID belongs to uid 1000 is disconnected through the X
  server (XRes client ids, `XKillClient`); (4) the modifier keys and mouse buttons 1 to 3
  are released. A stopped `xdotool type` resumed at
  hand back finds its display connection gone and exits, so it cannot finish typing into
  the field the person left focused, whatever it is called and wherever it was copied.
  Command-line work resumes at hand back; windows the agent opened itself are closed.
  Release order at hand back and at lapse: close the window (CAS), end the person's VNC
  session (rotate the passwords, else stop the stream, else put the computer to sleep),
  then thaw. The tool call that was in flight is discarded by the epoch fence, as today.
- **D4. The call that raises "Start <name>'s computer" only starts the computer.** It
  returns "Started your computer. Nothing else was done…" and the model repeats the
  action, which then goes through its own approval as usual. One approval authorises one
  thing, the digest stays over that one action, and the shell's own card still appears.
  Under `allowed` the first call starts the computer and performs the action.
- **D5. Tunnel tickets are minted by the host,** single use, 60 s, bound to one container
  and one port. The relay never holds the host's bearer token: the app asks the host for a
  ticket and hands it to the relay sealed inside the relay token (AES-256-GCM, key derived
  from `AUTH_SECRET`), so neither the browser nor a log sees it. The host cannot verify the
  app's relay token, because it holds no app secrets; the ticket is how it authenticates
  the tunnel.
- **D6. The host's broker is reached through a root-owned Unix socket** (the
  `deploy/exec-host` pattern), not sudo, so the host service can run with
  `NoNewPrivileges=yes`. The argv policy is the same `validate()` from
  `deploy/agent-computers/docker-broker.py`, imported, not copied.
- **D7. Per-plan computer entitlement and caps are a new map `PLAN_AGENT_COMPUTER` in
  `src/lib/plans.ts`,** not new `PlanConfig` fields. `PlanConfig` is the commercial record
  the billing surfaces read (`src/lib/billing/plan-capabilities.ts`, the plans page,
  Stripe price keys); leaving it untouched means no existing entitlement changes and no
  plan surface starts advertising computers while they are off. The caps are numbers with
  env overrides, which `PlanConfig` does not carry. A test holds the map's entitlement
  equal to `PLANS[plan].agents`.
- **D8. Streamed shell output is stored in a new table, `ComputerShellOutput`, and read by
  a new computer route,** not written as a new `WorkEvent` kind. `WORK_EVENT_KINDS` is a
  contract pinned by the native apps and owned by another job. The final, capped output
  still lands in the run as today.
- **D9. The scripted model needs one dev-only line in `src/lib/work/dispatch.ts`,** a file
  the Orbit runtime job owns, because dispatch refuses when no provider key is
  configured. The hook is inert unless `NODE_ENV` is not production, the opt-in variable is
  set, a script file is set, and the account is listed.
- **D10. DNS: the resolver exception is removed AND the provider's `--dns` is pinned to a
  never-routed sentinel with port 53 REJECTed,** so lookups fail at once instead of timing
  out. Removing `--dns` alone may let Docker's embedded resolver fall back to the host's
  own resolvers, and recent Docker releases forward to a loopback host resolver from the
  host's namespace, outside the bridge firewall (to be confirmed, not assumed); S2 proves
  the result on Docker 29.9.2 here.
- **D11. Two additions to decision 6:** x11vnc only accepts connections from the bridge
  gateway (`-allow 172.30.0.1`), so the agent cannot reach VNC on its own loopback; and
  every agent command starts through the exec launcher (D13), which sets `HOME=/home/agent`
  and a fixed `PATH` with `~/.local/bin` **appended**, and runs `bash --noprofile --norc -c`
  (fact 17). pip, venv and npm work, and no file the agent can write (`~/.profile`,
  `~/.bashrc`, a `~/.local/bin/ls`, `BASH_ENV`) runs before or instead of an approved
  command. Revision 1's `/etc/profile.d` line that prepended `~/.local/bin` is dropped.
- **D12. One addition to decision 5:** `AGENT_COMPUTER_REQUIRE_BROWSER_SANDBOX` (default 0)
  lets the owner refuse to wake a computer whose Chromium sandbox is off. Default 0 keeps
  today's behaviour (sandbox off) available and reported.
- **D13. Chromium's sandbox comes on only together with a namespace ban on the agent's own
  processes; without the ban it ships off.** A seccomp profile that permits user namespaces
  applies to the whole container, and inside a user namespace the agent's model-driven
  shell would hold every capability (`CAP_NET_ADMIN`, mount): kernel surface Docker's
  default profile closes today. The review proved it on this machine (Docker 29.9.2,
  `--cap-drop ALL`, `no-new-privileges`, `--user 1000`): under the default profile
  `unshare -Ur` fails with EPERM; with namespaces permitted it yields uid 0 and `CapEff
  000001ffffffffff` (`computers/plan-critic/userns-probe.txt`). So every uid-1000 exec starts
  through `/opt/juno/agent-exec` in the read-only image, which stacks a seccomp filter
  (python3-seccomp) that answers `unshare`, `setns` and `clone` with any `CLONE_NEW*` flag
  with EPERM and `clone3` with ENOSYS, cleans the environment, and then execs the command.
  Filters are inherited by every child and survive `execve`. The broker refuses a uid-1000
  exec that does not start with the launcher (fact 25). At every wake the provider checks
  the ban from the agent's side, and the sandbox reports `on` only when the kernel allows
  it and the ban holds; if the agent can create a namespace, the wake is refused. If S2
  cannot make the ban hold, the permissive profile is never installed and the sandbox is
  `off`, which is exactly today's configuration. The browser uid (1001: Xvfb, xfwm4, the
  gate, x11vnc, Chromium) keeps user namespaces when `on`; none of them runs model-written
  code. An AppArmor profile that lets only Chromium create namespaces was considered and
  not chosen: this machine has no AppArmor, ubuntu-latest runners have it, and the launcher
  behaves the same on both.
- **D14. Retention needs a switch of its own, and `COMPUTER_RETENTION_DAYS` is never
  honoured.** Three docs gave 30 days as the default (fact 15), so an owner may already
  have it in a production env file; reading it would start deleting files and sign-ins the
  day computers are enabled, with no owner decision. Deletion needs both
  `AGENT_COMPUTER_RETENTION_ENFORCE=1` and `AGENT_COMPUTER_RETENTION_DAYS` (a whole number,
  at least 7). The legacy variable, when set, is logged once as ignored. One parser,
  `src/lib/computer/retention.ts`; S1 removes the unread getter from `env.ts`.
- **D15. Under `ask`, the `browser` tool keeps the temporary per-run browser until a
  computer tool has started the computer in this run.** Routing it through the start card
  would change how every agent of an entitled account browses today (a card where there was
  none) and would park unattended browse routines, which then stay parked until someone
  presses Resume (section 7). Under `allowed`, or once the computer is on in this run,
  `browser` is the computer's browser. Decision 4 speaks of computer tools; this keeps it
  literal, and the prompt tells the model how to get its signed-in browser.
- **D16. "Outdated" means another image, not only another label.** `docker start` reuses
  the image a container was created from, so a Chromium security rebuild under the same
  label never reached existing containers, and revision 1's README sentence ("outdated
  containers are rebuilt on their next wake") would have been untrue. `isOutdated`
  compares the container's image ID with the current tag's, and a mismatch recreates the
  container on its volumes at the next wake. The image's build time is reported by host
  health and audited at wake against `AGENT_COMPUTER_MAX_IMAGE_AGE_DAYS` (†14), and setup can
  install a weekly rebuild timer (opt-in). An asleep container runs nothing, so recreating
  at wake also covers idle ones.
- **D17. Host tokens rotate and are namespaced.** The host accepts at most two tokens per
  environment at once (current and next), each bound to an environment namespace label
  (`juno.ns`) applied at create; listings, destroy, tickets, tunnels and every operation
  see only that namespace's containers and volumes. Rotation needs no simultaneous restart,
  and the host log names the token id used. A host never serves two environments under one
  token; the README says so.
- **D18. TLS between the web VM and the host defaults to a private CA that can sign
  nothing else.** Revision 1 reused exec-host's certbot path, which cannot renew behind
  the host's firewall (port 80 closed). Default now: `setup.sh` creates a CA with a
  critical `nameConstraints` extension limited to the host's name, signs the host's
  certificate, and destroys the CA key; the web VM trusts that CA through
  `NODE_EXTRA_CA_CERTS`, which therefore adds trust in exactly one name. No public port 80,
  no DNS-provider credentials. Let's Encrypt (standalone, with hooks that open port 80 only
  while a renewal runs) and an owner-supplied certificate stay available.
- **D19. Egress identity follows the container lifecycle, not a poll.** Revision 1 keyed the
  log and the budget by source IP through a map refreshed every 10 s, so a reused address
  inherited another computer's budget and a proxy restart reset it. Now the broker updates
  the address map before and after it starts, and before it stops or removes, a container;
  a root `docker events` watcher repairs it for containers that stop on their own; the
  proxy refuses an address the map does not know instead of guessing. The budget is kept
  per container name and persisted across proxy restarts, and the log goes to its own file,
  not journald, whose per-service rate limit can drop lines.

### S1.1 Access: rollout, entitlement, caps (`src/lib/computer/access.ts`)

```ts
export type ComputerRollout = "allowlist" | "plans" | "off";
export type ComputerAccessReason = "server_off" | "rollout_off" | "not_in_rollout" | "plan" | "unavailable";
export type ComputerAccess =
  | { ok: true; plan: Plan; caps: { maxEnabled: number; weeklyMinutes: number } }
  | { ok: false; reason: ComputerAccessReason; message: string; upgradePlan: Plan | null };

export function computerRollout(env?: NodeJS.ProcessEnv): ComputerRollout;
export function isAllowlisted(
  user: { id: string; email: string | null; emailVerified: Date | null }, env?: NodeJS.ProcessEnv
): boolean;
export function computerCapsFor(plan: Plan, env?: NodeJS.ProcessEnv): { maxEnabled: number; weeklyMinutes: number } | null;
export async function computerAccessFor(userId: string): Promise<ComputerAccess>;
```

Order of checks, first failure wins: a provider is configured (`server_off`) → rollout not
`off` (`rollout_off`) → under `allowlist`, the account is listed (`not_in_rollout`) → the
plan has `PLAN_AGENT_COMPUTER[plan]` non-null and both caps above 0 (`plan`) → the provider's
`available()` answers true (`unavailable`; cached 30 s per process, so a host outage costs
one request per 30 s, and checked last so an account that is not entitled never waits on
the host). Under `plans` the allowlist is not consulted. The allowlist is checked before the
plan on purpose: under `allowlist`, upgrading would not give an unlisted account a
computer, so telling it to upgrade would be untrue. A listed Free or Lite account gets the
upgrade sentence.

An allowlist entry with `@` matches only an account whose `User.emailVerified` is set,
compared case-insensitively; a user-id entry matches exactly whether or not the email is
verified. Credentials sign-up leaves `emailVerified` null, so without this anyone could
register an address the owner meant to list and pass, the way `usage.ts:137` and
`chat/turn/accept.ts:208` already refuse unverified accounts for spending.
`computerAccessFor` reads the plan, `email` and `emailVerified` from the database, never
from the session.

`src/lib/plans.ts` gains, without touching `PlanConfig` or `PLANS`:

```ts
export interface AgentComputerEntitlement { maxEnabled: number; weeklyMinutes: number }
/** Defaults; env overrides in src/lib/computer/access.ts. Non-null exactly where PLANS[plan].agents is true. */
export const PLAN_AGENT_COMPUTER: Record<Plan, AgentComputerEntitlement | null>;
export function cheapestPlanWithAgentComputer(): Plan;
```

### S1.2 Weekly allowance and metering

- `billComputerSeconds` records an `AgentComputerUsageInterval` (`createMany` with
  `skipDuplicates`, key `(agentId, startedAt)`) **before** its price check, so time is
  metered at price 0. The spend write keeps its own idempotency key, unchanged.
- `disableComputer` meters the open interval before it destroys (today it drops it).
- `computerAllowanceRefusal(userId, now)` = this week's intervals plus the accrued
  seconds of every awake computer of the account (`now - lastResumedAt`) against
  `weeklyMinutes`. Intervals count in the week they started.
- `computerUsageBudgetRefusal` (the name the sweep already calls, so `sweep.ts` needs no
  change) becomes: access refusal, then allowance refusal, then the existing spend check.
  It no longer returns null early when the price is 0, and the allowance part no longer
  returns null for a non-Prisma persistence: the in-memory persistence stores usage
  intervals too (`recordUsageInterval`, `sumUsageSeconds(userId, weekStart)`), so the
  in-memory tests exercise the real check instead of passing vacuously. Only the spend part
  keeps its Prisma-only path. Callers: `ensureAwake`, `renewComputerLease` (a refusal
  releases the lease, sleeps the computer, writes `lastError`, audits `slept` with the
  reason), and the sweep.
- The allowance is checked at wake, at every lease renewal (40 s) and at every sweep (60 s),
  never continuously, so it is soft: an account can overrun its week by at most (its awake
  computers) × 40 s for computers a run holds, and 60 s for one only a viewer keeps awake.
  `docs/OPEN_DECISIONS.md` records the bound with the caps.
- Enabled cap: a new persistence method `claimEnableSlot(userId, agentId, maxEnabled)` that
  counts the account's `AgentComputer` rows other than this agent's and inserts the row in
  one transaction under `pg_advisory_xact_lock(hashtext('juno.agent-computer.enabled:' || userId))`;
  the in-memory persistence gets the same method.

### S1.5 Lazy self-start in a Work run

Store (`store.ts`):

```ts

      /** The policy as stored now (re-read every call, never cached). */

       *  creation (enabled cap), disk, lease, wake. The attachment, once made, is memoized
       *  per run; the policy check is not. */

  userId: string; agentId: string | null | undefined; runId: string; attended: boolean; vision: boolean;
```

`none` when: no agent, the agent's `executionTarget` is `mac`, the policy is `off`, or
access is not ok (note null: the prompt says nothing, exactly as today in production;
for `unavailable` the note is "Your computer can't be reached right now; work without
it."). `resolveRunComputerSession` stays for callers that want an eager attach and is
reimplemented on `prepareRunComputer(...).start({ approvedStart: false })`.

Consent can be withdrawn mid-run, so `start` never trusts the policy the run began with:
`off` refuses with the "switched off" sentence and audits `refused` with
`reason: policy_off`; `ask` with `approvedStart: false` (an `allowed` run whose person has
since lowered the policy) refuses with the "now wants to be asked" sentence and does not
start, and the next call raises the card; an approved start whose policy has since gone to
`off` does nothing.

### S1.6 Takeover wiring and audit (store)

- `openComputerViewSession` control: after the takeover window opens and only when it is a
  new takeover (the epoch moved), call `provider.freezeAgent?.(handle)`. On failure:
  audit `freeze_failed`, keep the takeover (the person must get control), and return
  `freezeFailed: true` so the overlay shows the line in 4.3. A provider without the
  method: audit `freeze_unavailable`.
- One release path, `releaseTakeover(row, via)`, used by hand back, by lapse and by a
  control heartbeat refused for lost access, always in this order (D3): (1) close the
  window (`takeoverClosed()`, or the CAS below for a lapse); (2) end the person's VNC
  session: rotate the passwords (`ensureStream` with `rotatePasswords`, secrets persisted;
  rotation restarts x11vnc, which drops every connected client); if that fails, stop the
  stream (`stopVnc`); if that fails too, put the computer to sleep (which ends every
  process) and audit `slept` with `reason: rotate_failed`; (3) only after one of these
  succeeded, `thawAgent`; (4) audit. The agent never runs again while the person who held
  control can still type. A rotation failure is audited `rotate_failed`.
- Hand back (`heartbeatComputerViewSession` with `ended`): `releaseTakeover`, then audit
  `takeover_handed_back` with `via` (web or app) and `heldSeconds`.
- Lapse: `settleLapsedTakeovers(now)` finds rows with `takeoverBy` set and
  `takeoverUntil <= now`, and for each, through a new persistence CAS
  `closeLapsedTakeoverCas(userId, agentId, expectedUntil)` (applies only if `takeoverUntil`
  is unchanged): `releaseTakeover`, audit `takeover_lapsed`. Called from the runner tick and
  from `computerTakeoverFence` when it reads a lapsed row, so the person's session is gone
  and the agent's processes are thawed before the agent acts again. Today a control
  heartbeat that arrives after a lapse renews the same holder's window; once the lapse is
  settled the window is closed, so a late heartbeat no longer reopens it (the agent may
  already be acting) and the person takes control again, which freezes again. The overlay
  already says when control lapsed.
- A control heartbeat (not ended) checks access first; a refusal runs `releaseTakeover`
  with `via: access_lost` and answers 403 (S1.3).
- `ensureAwake` calls `thawAgent` when no takeover is active (idempotent safety net). It
  recreates the container on its volumes when `provider.isOutdated?.(handle)` is true (D16:
  another image; audit `rebuilt`, the existing `computer_recreated` event wording), and
  audits `image_stale` with `days` when `provider.imageInfo?.()` is older than
  `AGENT_COMPUTER_MAX_IMAGE_AGE_DAYS`.
- At each wake, `provider.browserSandbox?.(handle)`: its answer is audited
  `browser_sandbox`; a throw (the agent could create a user namespace, D13) puts the
  computer to sleep, audits `sandbox_check_failed`, and refuses the wake with the sentence
  in 4.3.
- Audit `woke`, `rested`, `slept`, `started`, `enabled`, `disabled`, `reset`, `refused`.

### S2.2 Egress audit log and bandwidth cap (`egress-proxy.py`, D19)

- Identity. `egress-map.py` (root, in the image's deploy directory, installed to
  `/usr/local/sbin/juno-computers-egress-map`) owns `JUNO_EGRESS_MAP`, a JSON object
  `{"gen": n, "entries": {"172.30.0.x": {"name": "juno-agent-…", "since": iso}},
  "releasing": ["172.30.0.y"]}`, written atomically (temporary file and rename) under an
  `flock`. Subcommands: `rebuild` (from `docker network inspect juno-computers`: running
  containers only), `release <name>` (drops the name's entries and lists their addresses
  as `releasing` until the next `rebuild`). Writers:
  - the broker, which now runs these operations as a child instead of `execve`: `rebuild`
    before and after `start`; `release <name>` before `stop` and `rm -f`, `rebuild` after.
    A container that died on its own cannot leave a stale entry that a new container on
    the same address inherits, because every start through the broker rebuilds first;
  - `juno-computers-egress-map.service` (root, `Restart=always`), which runs
    `docker events --filter type=network --filter type=container` and calls `rebuild` on
    every network connect or disconnect for `juno-computers` and every container `die`,
    and once at start. It repairs containers stopped outside the broker (a crash, an OOM
    kill, the kill switch). No timer, so `AccuracySec` does not arise.
- The proxy stats the map on every new connection and reloads it when `gen` changes. A
  mapped address is attributed to its name. A `releasing` address is refused (`unmapped`).
  An unknown address is re-checked every 100 ms for up to 2 s (the broker's post-start
  `rebuild` lands within that), then refused (`unmapped`). Nothing is attributed by guess.
- Log: one JSON line per connection, written when it ends, to
  `/var/log/juno-computers-egress/egress.jsonl` (`LogsDirectory=` of the proxy unit, 0750),
  not journald, whose per-service rate limit (`RateLimitIntervalSec`) can drop lines;
  logrotate keeps `JUNO_EGRESS_LOG_DAYS` († 14) days:
  `{"start": iso, "end": iso, "computer": "juno-agent-…" | null, "src": "172.30.0.x",
  "host": "<CONNECT host or Host header host>", "port": 443, "up": bytes, "down": bytes,
  "verdict": "ok" | "refused" | "over_budget" | "unmapped" | "error"}`. No path, query,
  header or body, ever. Refusals are logged too.
- Budget: per container **name**, a rolling hour of sixty one-minute buckets, both
  directions; over `JUNO_EGRESS_MAX_MB_PER_HOUR`, a new request gets 403 and an open tunnel
  is closed at its next chunk; logged `over_budget`. A new name starts empty, so a new
  computer on a reused address never inherits another's refusals. The buckets are
  persisted to `$STATE_DIRECTORY/budget.json` (`StateDirectory=` of the unit) every 10 s and
  at SIGTERM, and loaded at start, so a restart (the agent can force one by exhausting the
  proxy's `MemoryMax=96M`) loses at most 10 s of counts and never resets a budget.
- `setup-vm.sh` installs the map service, writes the `Environment=` lines and the
  `LogsDirectory=`/`StateDirectory=` settings into the proxy unit, and the logrotate file.

### S2.3 Chromium's own sandbox, and the exec launcher (D13)

- **The launcher.** `/opt/juno/agent-exec` (`agent-exec.py`, root 0755 on the read-only
  root, needs `python3-seccomp`). It refuses to run unless its uid is 1000. In every mode it
  first installs a seccomp filter (default allow; `unshare` and `setns` → EPERM; `clone`
  whose flags argument has any of `CLONE_NEWNS | CLONE_NEWCGROUP | CLONE_NEWUTS |
  CLONE_NEWIPC | CLONE_NEWUSER | CLONE_NEWPID | CLONE_NEWNET` → EPERM; `clone3` → ENOSYS so
  libc falls back to `clone`; x86_64 and aarch64), then replaces the environment with a
  fixed one: `HOME=/home/agent`, `USER=agent`, `LOGNAME=agent`,
  `PATH=/usr/local/bin:/usr/bin:/bin:/home/agent/.local/bin` (`~/.local/bin` last),
  `LANG=C.UTF-8`, `DISPLAY=:0`, the four proxy variables, `TERM=dumb`,
  `PIP_BREAK_SYSTEM_PACKAGES=1` (Debian 12 marks its Python externally managed, which also
  blocks `pip install --user`; the root filesystem is read-only, so nothing of the system
  is at risk), `NPM_CONFIG_PREFIX=/home/agent/.local`. Nothing passes through, so no
  `BASH_ENV`, `ENV` or exported bash function survives. Modes:
  - `run -- <argv…>`: model-driven work (the shell, the five input methods, the agent's file
    writes). Refuses with exit 75 and `frozen` on stderr while `/run/juno-state/frozen`
    exists (S2.4), else `execv`s.
  - `helper -- <argv…>`: the provider's own reads (realpath, stat, find, head, du, the
    screenshot script) and S5's upload by the person. Same filter and environment, no
    frozen check, so the person's file browser works while they have control.
  - `freeze`, `thaw`: S2.4.
- The shell becomes `agent-exec run -- timeout --signal=TERM --kill-after=5 <secs> bash
  --noprofile --norc -c <command>`: no login or rc file runs (fact 17), and `cwd` stays the
  validated `--workdir`.
- **The broker** requires, for every `exec --user 1000`, that the element after the
  container name is `/opt/juno/agent-exec` followed by `run --`, `helper --`, `freeze` or
  `thaw` (fact 25). `isVncRunning` moves to uid 1001 (`pgrep` ran as 1000).
- **The profile.** `seccomp-chromium.json`: Docker's default seccomp profile for the
  installed Docker version (moby `profiles/seccomp/default.json`, Apache-2.0, vendored
  beside it as `seccomp-docker-default.json` with its source tag), plus only what
  Chromium's namespace sandbox needs, found on this machine: expected to be `clone` and
  `unshare` with `CLONE_NEWUSER` and the namespace flags Chromium combines with it, and
  `chroot`; `clone3` keeps the default's ENOSYS answer unless Chromium is shown to need it.

### S2.4 Takeover primitives and VNC (D3)

- A new tmpfs `/run/juno-state` (uid 1001, mode 0755, 64 KB) in the create argv and the
  broker's fixed tmpfs list: uid 1000 can read it, only uid 1001 can write it. It holds
  the frozen marker and the sandbox state. `/run/juno` stays 0700 for secrets.
- `freezeAgent(handle)`, each step through the broker, any failure a `ComputerError`:
  1. as uid 1001: `touch /run/juno-state/frozen` (from now on `agent-exec run` refuses);
  2. as uid 1000: `agent-exec freeze`, which sends `kill(-1, SIGSTOP)` (every uid-1000
     process but itself; the kernel walks the set under the task-list lock, and a fork
     caught in progress either hands the signal to its child or is restarted), then scans
     `/proc` for a uid-1000 task other than itself not in state T or Z, repeating the
     signal and the scan up to 10 times 50 ms apart; exit 0 when none is left, 3
     otherwise. A launcher that was already past its marker check is a uid-1000 process
     and is stopped with the rest;
     one that starts later sees the marker. That closes the race with a command that passed
     the takeover fence just before the window opened;
  3. as uid 1001: `/opt/juno/x-clients.py close-uid 1000` (`python3-xlib`): asks the X
     server for its clients and their PIDs (XRes `QueryClientIds`, which Xvfb fills from
     the socket's peer credentials, so a renamed or copied program cannot hide) and calls
     `XKillClient` on every client whose PID belongs to uid 1000. A stopped injector resumed
     at thaw finds its connection gone and exits; it can never finish typing;
  4. as uid 1001: `xdotool keyup` for Shift, Control, Alt, Super, Meta and ISO_Level3 (left
     and right) and `mouseup` for buttons 1, 2 and 3, so a chord or drag cut half way never
     leaves a key held for the person.
  If S2 finds on this machine that Xvfb does not report client PIDs, step 3 falls back to
  SIGKILL of every stopped uid-1000 process whose `/proc/<pid>/exe` is `/usr/bin/xdotool` or
  `/usr/bin/scrot`, and section 7 records that a copied or scripted injector then survives
  stopped and can resume typing at thaw. That fallback is reported, never presented as the
  design.
- `thawAgent(handle)`: as uid 1001 `rm -f /run/juno-state/frozen`, then as uid 1000
  `agent-exec thaw` (`kill(-1, SIGCONT)`). A provider helper caught by the freeze (a `du`,
  a poster) times out as any slow call does.
- `startVnc`: on Linux add `-allow <gateway of the computers network>` (172.30.0.1 as
  setup-vm.sh creates it); macOS development keeps today's arguments. Passwords stay 8
  characters (the RFB limit) and keep rotating.
- `isOutdated(handle)` (D16): the container's `inspect -f '{{.Image}}' <name>` differs from
  `image inspect --format '{{.Id}}' <image>`. `imageInfo()`: `image inspect --format
  '{{.Id}}\t{{index .Config.Labels "juno.security"}}\t{{.Created}}' <image>`. The broker
  gains exactly these two formats and the container one.
- `state()` (fact 23): `missing` only when Docker says the container does not exist. The
  broker's namespace check exits 3 with `missing` for "No such container" or "No such
  object" and 1 for anything else; `docker.ts` maps exit 3 (or that text) to `missing` and
  throws `ComputerError(COMPUTER_UNREACHABLE)` for every other failure, so a daemon hiccup
  never recreates a computer.

## S3. The remote computer host and RemoteComputerProvider

**Goal.** Computers run on their own Linux machine. The web VM talks to it over a narrow,
authenticated HTTPS API that covers exactly the `ComputerProvider` operations, plus
WebSocket tunnels for CDP and VNC that reach only containers that host created and only
ports 9222 and 5900. The host holds no app secrets. The relay and the Work runner use the
tunnels when the provider is `remote`. Same-host Docker stays for development and a
single-box install.

**Owns.** New `deploy/computer-host/` (`juno-computer-host.py`, `juno-computer-host-broker.py`,
`setup.sh`, `README.md`, `local/run-local.sh`); new `src/lib/computer/remote.ts`;
`provider.ts`, `types.ts`, `docker.ts`, `fake.ts`, `remote-browser.ts`, `live-view.ts`,
`store.ts`, `sweep.ts`, `retention.ts`, `audit.ts`, `errors.ts`, `docker-cli.ts`;

### S3.1 The host service (`deploy/computer-host/juno-computer-host.py`)

Python standard library plus `python3-websockets`. Two listeners on 127.0.0.1: the API
(`apiPort`, threaded `http.server`) and the tunnels (`tunnelPort`, asyncio websockets), in
one process sharing the ticket store. nginx terminates TLS on 443 and routes `/v1/tunnel`
to the tunnel port with Upgrade headers, everything else to the API (S3.4 has its
timeouts).

- **websockets version.** Debian 12 and Ubuntu 24.04 ship `python3-websockets` 10.4, newer
  distributions 13 to 14, whose default API differs. The host imports
  `websockets.legacy.server` and `websockets.legacy.client` explicitly (present from 10.0
  through 14.x); `setup.sh` refuses a version outside [10.4, 15) and says which it found;
  tests run against 10.4 in a venv.
- **Both legs** of a tunnel use `max_size=64 MiB` (the gate's own limit; the library's
  1 MiB default would close the tunnel on a large CDP reply such as a screenshot),
  `max_queue=32`, `ping_interval=30`, `ping_timeout=30`.
- **Tokens (D17).** `tokensFile` holds `{id, sha256, namespace}` entries, at most two per
  namespace; SIGHUP re-reads it, so adding or retiring a token restarts nothing. Each
  request's bearer token is format-checked (64 hex, or at least 43 base64url characters),
  hashed, and compared with `hmac.compare_digest` against every stored hash (no early
  exit); the match fixes the request's namespace. The service refuses to start if any entry
  is malformed or a namespace has more than two tokens. The log names the token id, never
  the token.
- **Namespaces (D17).** `create` adds `--label juno.ns=<namespace>` to the container and both
  volumes. Every operation on a name first checks, through the broker's namespace inspect,
  that `app=juno` and `juno.ns` equal the request's namespace; `listOwned` and volume
  listings filter by `label=juno.ns=<namespace>`; tickets and tunnels are bound to the
  namespace too. The broker's host mode requires the fourth label; the single-box Docker
  provider keeps three. Agent ids are unique per database, but a staging database restored
  from production shares them: such an environment gets a name conflict on create, never
  another environment's computer, and the README says to give each environment its own
  host.
- Container names must match `juno-agent-[A-Za-z0-9_-]{1,120}`. Every Docker call goes
  through the broker socket (D6): `/run/juno-computer-host/broker.sock`,
  root:juno-computer-host 0660, socket-activated, one JSON request `{argv, stdin_b64?}` per
  connection, framed stdout/stderr/exit back, `validate()` and the namespace inspect of
  `main()` imported from `deploy/agent-computers/docker-broker.py` (refactor `main()` so both
  entry points share one function, including S2's egress-map hooks), with the host's policy
  file and the same fixed environment.
- **Missing vs failing.** A Docker "No such container" (the broker's exit 3, S2.4) is the
  only answer that becomes HTTP 404 `{error: "no_such_container"}`; every other daemon or
  broker failure is 502 `{error: "host_error"}`, so the app never mistakes an outage for a
  deleted computer.
- **Logs.** `BaseHTTPRequestHandler.log_message` is overridden: operation, container name,
  token id, status, duration. Never the request line, a path or query (users' file paths
  travel in `?path=`), a command, file content, a token, a password or a ticket.

### S3.2 RemoteComputerProvider (`src/lib/computer/remote.ts`)

- `name: "remote"`. Refuses to construct (the factory returns null and logs once) when the
  URL is not `https:`, unless it is `http:` to a loopback host outside production, or when
  the token's format is wrong.
- HTTP errors and timeouts become `ComputerError(COMPUTER_UNREACHABLE)` with a scrubbed
  detail; a host body is never shown to anyone. Idempotent GETs retry once on a network
  error.
- `state()` returns `missing` only for a 404 `no_such_container`; a transport error, a
  timeout or any 5xx throws `COMPUTER_UNREACHABLE`, never `missing` (fact 23), so a host
  outage can never send `ensureAwake` into a recreate. `available()` answers false when the
  host does not answer (S1's `unavailable`).
- `endpoints(handle)` returns tunnel descriptors. `Endpoints` becomes
  `{ cdpUrl: string; cdpHeaders?: Record<string, string>; vncHost: string; vncPort: number;
  vncTunnel?: { origin: string; ticket: string } }`; Docker fills the first three as today.
  `cdpHeaders` carries `X-Juno-Tunnel-Ticket`.
- `screenshot` converts PNG to JPEG with `sharp`, as `docker.ts` does.
- `types.ts`: `name: "docker" | "fake" | "remote"`; the five S2 methods become required;
  `fake.ts` implements them (it already does from S1).
- Lockstep test (`tests/computer-host-argv.test.ts`): the host's `--print-argv <op> <json>`
  mode prints the argv it would send for each operation; the test compares it with the argv
  builders `docker.ts` exports for the same inputs.

### S3.3 Tunnels in the app, the runner and the relay

- `remote-browser.ts`: when `endpoints()` gives `cdpHeaders`, connect to `cdpUrl` as given
  (no path rewrite) with those headers plus `X-Juno-Cdp-Token`, and no subprotocol. A
  reconnect asks `endpoints()` again, so it gets a fresh ticket.
- `live-view.ts` `mintViewToken`: version 2 for a tunnel:
  `{v: 2, a, u, m, exp, j, r: <host origin>, k: <sealed ticket>}`. Sealing: AES-256-GCM with a
  key from HKDF-SHA256(`AUTH_SECRET`, salt `juno-computer-view-v2`, info `tunnel-ticket`);
  the plaintext is `{t: <ticket>, p: 5900}`, and the additional authenticated data is the
  token's other fields (`v|a|u|m|exp|j|r`), so a sealed ticket cannot be lifted into
  another token. Version 1 stays for Docker. `resolveComputerRelayUrl` reads
  `COMPUTER_VIEW_RELAY_URL` first, then today's variables.
- `relay/src/computer-view.ts`: accepts v1 as today; v2 only when `m` is `watch` or
  `control`, `r` is in `RELAY_COMPUTER_HOSTS` and `wss:` (or loopback `ws:` outside
  production), the unsealed `p` is 5900, and the AAD matches; opens `<r>/v1/tunnel` with
  the ticket in `X-Juno-Tunnel-Ticket`, no subprotocol, and `rejectUnauthorized: true`
  (trusting the CA through `NODE_EXTRA_CA_CERTS`, D18); pipes binary frames with the
  existing backpressure, idle, duration, per-agent and single-use rules.
- CSP (out of area, minimal): `buildCsp` in `src/lib/csp.ts` takes an optional
  `computerRelayUrl`, added to `connect-src` beside `relayUrl`; `src/middleware.ts` passes
  `process.env.COMPUTER_VIEW_RELAY_URL`. Voice keeps reading only its own variables.
- `store.ts`: `openComputerViewSession` asks the provider for the VNC endpoint per session;
  `AGENT_COMPUTER_REQUIRE_BROWSER_SANDBOX=1` makes `ensureAwake` refuse and sleep a computer
  whose `browserSandbox` is `off` ("This server requires the browser's own sandbox, and this
  computer can't use it.").
- **Losing the host mid-run.** The sweep (whose per-row catch S2 added) writes
  `lastContactAt` after every successful `state()`. When `state()` throws
  `COMPUTER_UNREACHABLE` for an awake row: the open interval is settled up to
  `lastContactAt` (metered and, at a price above 0, billed), `lastResumedAt` is cleared so
  nothing accrues during the outage, and `host_unreachable` is audited once; the row is
  otherwise left alone, never recreated or marked missing. At the first successful contact
  afterwards `lastResumedAt` becomes that moment and `host_reachable` is audited with the
  outage's minutes. `listOwned()` throwing skips orphan reaping for the pass. Tool calls
  return the `COMPUTER_UNREACHABLE` sentence; lease renewal failing with it keeps the lease
  and the run (the next call tells the model); the panel shows the `unavailable` line.
- The sweep passes `recordComputerAudit` as S2's retention audit writer, and audits
  `image_stale` once a day per host image when past the maximum age.

### S3.4 Host setup and the owner guide

- `deploy/computer-host/setup.sh --web-ip <ip> --domain <name> [--tls private|certbot|own]
  [--certbot-email <e>] [--cert <f> --key <f>] [--namespace <ns>] [--ssh-from <cidr>]
  [--max-running N]`, modelled on `deploy/exec-host/setup.sh`: packages (and the
  websockets version check), user `juno-computer-host` (no login, no docker group, no sudo),
  the broker socket and policy (host mode), the shared steps of `setup-vm.sh` (network,
  egress proxy with its log, budget and state directories, the egress map service,
  firewall, seccomp decision, image build) run through a new `setup-vm.sh --computer-host`
  mode that skips the sudoers rule for an app user, the service unit
  (`NoNewPrivileges=yes`, `ProtectSystem=strict`, no capabilities, `MemoryMax`,
  `TasksMax`), nginx, nftables, and the first token. Maintenance flags: `--add-token
  --namespace <ns>`, `--retire-token <id>`, `--renew-tls`, `--rebuild-image`,
  `--rebuild-timer on|off`.
- **Firewall.** The nftables table `inet juno_computer_host` has an input chain with
  `policy drop` accepting: `iif lo`; established and related; ICMP; SSH from `--ssh-from`;
  443 from `--web-ip`; and `iifname "br-juno" ip daddr 172.30.0.1 tcp dport 3128 accept`.
  Revision 1 copied exec-host's chain without that last rule, and because a drop in any
  nftables base chain is final (the iptables accept in `firewall.sh` lives in another
  table), every computer would have lost its only way out. Only the input hook is touched;
  Docker's own forward and NAT rules are left alone. On Azure the address the host sees
  may be the web VM's public address (outbound SNAT) rather than its private one: the
  README recommends one VNet and private addresses, and `setup.sh` ends by printing the
  check: from the web VM, `curl` the host's `/v1/health` with the token and compare its
  reported source address with `--web-ip`.
- **TLS (D18).** `--tls private` (default): `setup.sh` creates an EC P-256 CA whose
  certificate carries a critical `nameConstraints` permitting only `<domain>`, signs the
  host's certificate (SAN `<domain>`, 397 days), then shreds the CA key, and prints the CA
  certificate for the web VM's `NODE_EXTRA_CA_CERTS` (app, Work runner and relay). Renewal
  (`--renew-tls`) makes a new CA; the trust file may hold both CAs during the switch. Host
  health reports the expiry, and the README asks for renewal a month ahead. `--tls certbot`:
  `certbot certonly --standalone` with a `--pre-hook` that adds `tcp dport 80 accept` to the
  chain and a `--post-hook` that removes it, and a `--deploy-hook` that reloads nginx; port
  80 is open only while a renewal runs. `--tls own`: the given files. Revision 1's
  `--nginx` certbot path could not renew behind the firewall, so the certificate would have
  expired within 90 days.
- **nginx.** The path-free access log of `deploy/exec-host/setup.sh:209-210` (method,
  status, bytes, time; no request path, no query). `client_max_body_size 30m`. Locations:
  `/v1/tunnel`: Upgrade headers, `proxy_buffering off`, `proxy_read_timeout 300s`,
  `proxy_send_timeout 300s` (pings every 30 s on both legs keep a quiet tunnel far inside
  that; total lifetime is bounded by the relay's 2 h for VNC and by the run for CDP);
  `~ ^/v1/computers/[^/]+/exec$`: `proxy_read_timeout 330s` (300 s command limit, 5 s
  kill-after, margin), `proxy_buffering off` and `proxy_request_buffering off` (S5 streams
  NDJSON through it); everything else `120s`.
- **Token rotation (D17).** `--add-token` prints a new token and adds its hash; the host
  then accepts the old and the new. The owner sets the new one on the web VM and restarts
  the app, runner and relay whenever convenient (in-flight work keeps the old one until
  then), then runs `--retire-token <old id>`. Nothing is restarted on the host.
- `deploy/computer-host/local/run-local.sh`: the development profile on 127.0.0.1, broker in
  developer mode (same `validate()`, the local Docker socket), a generated tokens file,
  never for a shared host. `--nginx` also starts the generated nginx config in the official
  nginx image (`docker run --network host`) on 127.0.0.1:8443 with a private name-constrained
  CA for `localhost`, so the tested path is the production path.
- `deploy/computer-host/README.md`, the owner guide: what the host is for and why it is
  separate; sizing arithmetic (section 8); the commands in order; the web-VM env
  (`COMPUTER_PROVIDER=remote`, `COMPUTER_HOST_URL`, `COMPUTER_HOST_TOKEN`,
  `NODE_EXTRA_CA_CERTS`, relay `RELAY_COMPUTER_HOSTS`, keep `AGENT_COMPUTER_ROLLOUT=allowlist`,
  add accounts to `AGENT_COMPUTER_ALLOWLIST`); one host per environment; token rotation; the
  smoke to run on the host before allowlisting anyone; the kill switch; image freshness
  (`--rebuild-image` runs `docker build --pull --no-cache`, checks the label, prunes
  `juno-computer` images no container uses; containers made from an older image are
  recreated on their volumes at their next wake, D16; `--rebuild-timer on` installs the
  weekly timer); where the egress log is (`/var/log/juno-computers-egress/egress.jsonl`).
- OPERATIONS.md gains the remote section and the rollout, caps and allowance section.
- Check how the relay process receives its environment in production
  (`deploy/ecosystem.config.js`, owned by the Orbit runtime job). If `RELAY_COMPUTER_HOSTS`
  or `NODE_EXTRA_CA_CERTS` needs a line there, it is a minimal out-of-area edit named in

## 7. What stays open after this plan

Recorded so nobody reads this plan as closing them:

- The CDP gate is a pass-through (no method allowlist). Acceptable while only the app holds
  the token and no tool exposes raw CDP; needed before any tool does.
- A page flooding protocol events, or a message over 64 MB, stops the gate and the
  computer.
- `AllowFileSelectionDialogs` is undecided: the file dialog as uid 1001 can upload profile
  files.
- Image rebuilds (Chromium updates) run by hand or by the opt-in weekly timer (D16).
  Containers made from an older image are recreated at their next wake, and a stale image
  is reported, but by default nothing forces a rebuild or refuses a stale image (owner
  decision 16).
- An approval card shows a command, not the files it reads. The launcher closes the paths
  that ran on every command whatever its text (login and rc files, `BASH_ENV`, a
  `~/.local/bin` entry shadowing a system command), but a script the agent wrote, and
  configuration a named tool reads from the agent's home (`.npmrc`, `.gitconfig`, a
  `usercustomize.py` or `.pth` file under `~/.local`), still run with an approved command.
  The person approves running that tool in a computer the agent has written to.
- When Chromium's sandbox is `on`, the browser uid's programs (Xvfb, xfwm4, the gate,
  x11vnc, Chromium's browser process) may create user namespaces; none runs model-written
  code. The agent's processes cannot (D13).
- At take over, windows the agent opened itself are closed (their display connection is
  cut). If Xvfb on a host does not report client PIDs, the fallback only kills `xdotool`
  and `scrot` by path, and a copied or scripted injector survives stopped (S2.4 records
  which was used).
- The weekly allowance is soft by at most (awake computers) × 40 s, or 60 s for a computer
  only a viewer keeps awake (S1.2).
- An account that lost access cannot download files from its computer: the files route
  goes through the same gate as a wake (section 10, R16). An export path for downgraded
  accounts is owner decision 10.
- One host per environment: a staging database restored from production shares agent
  ids, and on a shared host it would meet name conflicts (D17 keeps the environments'
  computers apart, not their names).
- `Xvfb -ac` stays: uid 1000 must drive the display by design (the review's correction).
- Pixel clicks on submit controls are not escalated unless the page takes payment.
- The disk quota is measured, not enforced by the filesystem.
- The egress proxy allows any public host on 80 and 443 (owner decision 5).
- Answering a parked run does not requeue it (the Orbit runtime job's fix). Until it
  lands, an unattended run parked on "Start {name}'s computer" needs Resume after approval,
  like any parked approval today.
- The native apps show nothing new: they keep hiding the computer when `computer` is null,
  and the policy control and access line are web only. Native parity is a follow-up that
  needs a Mac to compile.

## 8. Owner decisions

Defaults are what ships; nothing changes until the owner says so.

1. **The computer host.** A dedicated Linux AMD64 VM (recommended; it can later also carry
   `juno-exec`) or a hosted sandbox vendor (a new subprocessor in `docs/SUBPROCESSORS.md`, a
   DPA, per-second billing). Region: same as the web VM (Azure Sweden Central) for latency
   and EU residency. Size, by arithmetic from the caps, not a measurement: each awake
   computer is capped at 2 GB RAM (no swap) and 2 CPUs; reserve 2 GB for the OS, Docker,
   proxy and service, and keep the 1 GB free-memory floor; so 6 awake computers need about
   16 GB RAM, plus disk for the image (about 1.8 GB), the 10 GB free-disk floor and up to
   10 GB per enabled computer (soft quota). Who holds SSH (`--ssh-from`) and the domain.
   One host per environment (D17).
2. **Which plans and how much.** Default: every plan where `agents` is true (Pro and up).
   Computers per account and awake minutes per week per plan (4.2). Awake caps per account
   (2) and per host (6).
3. **The price.** `COMPUTER_COST_MICRO_USD_PER_SECOND`, default 0. At 0 the weekly allowance
   still bounds use; above 0 computer time also draws on the usage windows.
4. **Rollout.** Who is on `AGENT_COMPUTER_ALLOWLIST` first (owner and staff), and when, if
   ever, to switch to `plans`.
5. **Egress.** Any public host on 80 and 443 (today) or an allowlist; the per-computer
   budget (1024 MB per hour); how long the egress log is kept (14 days by default; it names
   the hosts each computer reached, so it is personal data about what an agent did).
6. **Unattended command grants. Default: no.** Shell, typing and text keys ask every time;
   an unattended run notifies and parks. Any narrower grant ("may run commands in its own
   computer") would need an egress allowlist for that computer, an audit of commands and
   connections, plan gating, and would never cover typing into pages or payments.
7. **Retention.** Off. Turning it on needs `AGENT_COMPUTER_RETENTION_ENFORCE=1` and
   `AGENT_COMPUTER_RETENTION_DAYS` (at least 7); it deletes files and sign-ins and needs a
   user notice first. A `COMPUTER_RETENTION_DAYS` already in an env file does nothing
   (D14).
8. **Chromium's sandbox.** Whether to require it (`AGENT_COMPUTER_REQUIRE_BROWSER_SANDBOX=1`).
   It comes on only with the launcher's namespace ban (D13), and it depends on the host's
   kernel and AppArmor: on Ubuntu 24.04, whose AppArmor restricts unprivileged user
   namespaces by default, it will report `off` unless the owner relaxes that restriction
   on the host. S2 records what this machine allows, not what a production host allows.
9. **Uploads and logs.** The inbox cap (25 MB) and the streamed-output cap per call (512 KB).
10. **Downgraded accounts.** Today's plan: their computers stay asleep and intact; they can
    delete them but not wake them. Whether to offer an export first.
11. **The default policy for new agents.** `ask` in this plan.
12. **The review items in section 7** that need a decision (`AllowFileSelectionDialogs`).
13. **TLS for the host (D18).** The private name-constrained CA (default, renewed yearly with
    `--renew-tls`), Let's Encrypt with port 80 opened only during renewals, or the owner's
    own certificate.
14. **Host tokens (D17).** How often to rotate (`--add-token`, then `--retire-token`), and who
    holds them.
15. **Required CI.** Promoting `computer-e2e` to a required job after three consecutive
    green CI runs on a pre-flight branch (S4.2).
16. **Image freshness (D16).** `AGENT_COMPUTER_MAX_IMAGE_AGE_DAYS` (14), whether to install
    the weekly rebuild timer (`--rebuild-timer on`; it pulls Debian packages on the host),
    and whether a stale image should ever refuse a wake (today: reported only).
